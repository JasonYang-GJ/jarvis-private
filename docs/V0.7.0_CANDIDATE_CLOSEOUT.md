## Gate4C 焦点问题

真实入口位于 `MainWindow.xaml.cs` 的 `AskPointerQuestionButton_Click`。点击确认框后，它立即调用 `PreparePointerRegionAsync`；Host 的 `WindowsPointerDesktopProbe` 读取当时的前台窗口和指针位置。没有等待用户回到目标窗口或临时快捷键入口。

仓库外诊断程序直接实例化真实 Release MainWindow，加载实际资源，并调用真实点击处理逻辑。它停用 Loaded 的 Host/语音启动，用 fake API 在 Prepare 边界记录前台关系并抛出固定错误，确保捕获、OCR、Provider、凭据请求均为 0。所有确认仅为合成测试，不授权真实捕获。

首次诊断受到宿主资源加载和前台激活条件影响，不能作为产品结论。补齐测试宿主资源，并采用已有桌面验收相同的 SetForegroundWindow/UI Automation SetFocus 后，最终结果为：

```json
  "status": "REPRODUCED_WRONG_FOREGROUND",
  "prepareCount": 1,
  "foregroundBeforeClickIsClient": true,
  "foregroundAtPrepareIsZero": false,
  "foregroundIsClient": true,
  "foregroundIsExternalTarget": false,
  "captureRequests": 0,

```

诊断结果文件 SHA-256：`288126B441D5C65BDE495BD6D854F400617632A3C20C9FC88745B9009320B76A`。源码和结果留在本轮仓库外 evidence 目录；未保存屏幕、OCR、个人窗口标题或用户内容。

该结果证明现有点击链路没有把外部目标保持到 Prepare；它不证明实际 OCR 读到了哪段文字，也不代替人工捕获同意或 Gate4C 完整验收。

另有两个代码确认的约束：

1. 出站确认和提交前再次要求原目标仍是前台；回到元枢点击确认会改变前台。
2. `PointerAnswerPreparedConsent.Create` 把出站到期时间设为原锚点创建时间加 10 秒。识别、阅读完整预览、确认都占用同一时间预算。

因此不能简单增加等待、删除前台核验、延长全局锚点寿命，或用 IPC 工具维持前台后宣称真实 Client 已通过。具体变更方案见 [Gate4C 交互修复与验收方案](V0.7.0_GATE4C_INTERACTION_PROPOSAL.md)。
